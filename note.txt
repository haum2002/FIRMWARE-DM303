Hard truth
----------
- Do not claim the firmware is stable, accurate, low-latency, EMI-resistant, or
  True RMS improved unless the exact build has passed device-side tests.
- Do not claim ADC/True RMS/math/noise fixes unless the exact code path and
  calibration data are proven.
- Do not claim Malay UI, dark theme, clock/date, battery percent, or flashlight
  changes are complete unless they are visible on the device.
- No firmware package is accepted for flash right now.
- `V4.0.1h` is failed/quarantined unless a repair profile explicitly rebuilds
  it from official V4.0 with the failed resource/UI changes removed.

What likely went wrong

- Later builds mixed measurement-code patches, UI resources, language resources,
  logo/icon changes, and boot-delay changes. This made failures hard to isolate.
- Some text/resource changes were not layout-compatible with the vendor files.
- UI/resource restoration fixed smear symptoms but did not improve measurement,
  which means measurement failure is probably elsewhere.
- User correctly identified another packaging problem: several failed versions
  did not pull the SD-card `system` files accurately.
- Audit confirms `firmware-candidates/v4.0.1-beta/system` is only a partial
  overlay, with 28 official files missing and 37 official files changed. It
  must not be used as a complete SD-card `system` folder.
- Audit confirms `dm303_firmware/DM303-V4.0.1-beta/system` is contaminated
  compared with official V4.0, with 37 changed official files and extra
  generated resources.

Evidence that must guide the next step
--------------------------------------
- Backup V3.16 switches DC/AC more smoothly but has its own weaknesses.
- Backup V4.0 is the official baseline for V4.x.
- Manual says green mA/uA current path is below 200 mA and protected by a 0.5 A
  self-recovery fuse.
- Hardware photos show relays, protection parts, analog support ICs, external
  SPI flash, CR1220, and separate current-path circuitry.
- Reading and battery icon disappearing together suggests shared acquisition or
  status refresh failure, not only a display drawing issue.

Rules before any new flash candidate
------------------------------------
1. Build from official `backup/DM303 V4.0-read only/DM303V4.004.bin`.
2. Keep UI resources official until measurement behavior is isolated.
3. Do not include dark theme, logo changes, Malay slot changes, boot-logo delay,
   or exp15 aggressive gates in the measurement baseline.
4. Produce the build under analysis or firmware-candidates first, not directly
   in `dm303_firmware/DM303-V4.0.1-beta`.
5. Provide exact SHA-256, byte diff, expected offsets, rejected offsets, and
   validation output before asking the user to consider flashing.
6. Mark the package as HOLD unless the user explicitly accepts the risk.

2026-07-17 three-way vendor comparison -> v401h-repair-j (V4.0.1q)
-------------------------------------------------------------------
- Full three-way analysis V3.13 (US240104 update, first time analyzed) vs
  V3.16 vs V4.0: `docs/v313-v316-v40-switching-comparison-2026-07-17.md`.
- Key result: V3.13/V3.16 share V4.0's identical `0x3a98` guards and switch
  smoothly, so the repair-a..i guard caps were never the cause. V4.0
  redesigned acquisition: V3.x streams ADC-EOC ISR samples into a shared
  600-entry ring (screens just consume it); V4.0 polls DRDY synchronously
  per screen. In V4.0's ammeter AC<->DC switch-state handler (state `0x2d`)
  the acquisition window is overwritten with 600 samples at `0x1df0c`
  (`mov.w r0,#0x258`) or 360 at `0x1df40` (`mov.w r0,#0x168`) on every
  switch; 600 polled samples match the reported ~30 s blank.
- `v401h-repair-j` is built as a strict single-change candidate: official
  V4.0 + both windows lowered to the vendor's own 240 (`movw r0,#0xf0`,
  `40 f2 f0 00`, flag-safe, 4-byte in-place). NO repair-i guard caps, NOPs,
  cmp changes, or 64-sample window. Visible marker `V4.0.1q`, firmware
  SHA-256 `ecd7b5dc85158467ce9e2ffc8b71fd1523c934383c7d1e6677b7bd0f79e34642`.
- Profile registered in `dm303_v401_beta_patch.py`,
